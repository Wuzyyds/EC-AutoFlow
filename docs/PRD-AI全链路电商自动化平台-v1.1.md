### 0.1 v1.1 重点优化摘要

本版本不是简单扩写功能，而是把文档从“产品愿景”推进为“可用于立项评审的实施基线”。主要补强：

1. 锁定 Amazon 单一区域 MVP，解决“愿景覆盖 8 平台、首期验收却要求 4-5 平台”的冲突。
2. 增加平台能力矩阵，不再假定所有平台都支持同一套商品、客服、广告和财务接口。
3. 增加 RBAC、职责分离、审批状态机、不可篡改审计、限额和 Kill Switch。
4. 增加 PII 最小化、跨境数据、日志脱敏、数据保留与删除要求。
5. 增加 AI 用例风险分级、黄金集评测、提示词/模型版本、灰度和回滚机制。
6. 将“净利”修正为经营贡献利润口径，明确系统不替代法定会计总账。
7. 删除规避平台限制的设计，竞品数据只允许使用经授权、经法务确认的数据源。
8. 增加 SLO、RTO/RPO、备份恢复、成本预算、RACI 和生产 Go/No-Go 门禁。

# 第一部分：产品定义

## 1. 背景与问题

### 1.1 行业现状

2026 年跨境电商的核心矛盾已经变化。早期靠「信息差 + 铺货」就能赚钱，现在：

- **人力成本结构恶化**：一个成熟运营的日常工作里，约 60% 是重复劳动（导表、改价、跟库存、算利润、回客服话术），只有 40% 是真正的判断工作（选品、定价策略、广告结构）。
- **数据源分散**：选品数据在卖家精灵/Keepa，广告数据在 Amazon Ads 后台，订单数据在各平台卖家中心，财务数据在 Excel，客服数据在平台工单 —— 五套系统、五套口径。
- **决策窗口被压缩**：TikTok Shop 的爆品窗口从「刷到视频」到「跟品上架」只有 7-14 天，人肉流程根本跟不上。
- **隐性成本失控**：只看采购价和售价的毛利，忽视头程、仓储、退货率、广告 TACOS，导致「账面赚钱、实际亏钱」。

### 1.2 现有方案的缺口

市面上的工具各管一段：

| 类型 | 代表 | 缺口 |
|---|---|---|
| 选品工具 | Helium 10、卖家精灵、Kalodata | 只给数据，不给「选品表 + 上架模板 + 利润模型」的闭环产出 |
| ERP | 店小秘、领星、马帮 | 强在订单/打单，弱在 AI 分析、竞品监控、利润归因 |
| 广告工具 | Amazon Ads 后台、SaaS 广告工具 | 只管广告，不与库存、利润、选品联动 |
| 客服工具 | 平台自带工单 | 不做分类统计，不做售后自动化 |
| 财务 | Excel | 纯手工，口径不统一，无预警 |

**没有一个系统把 8 个环节串成一条自动化流水线。**

### 1.3 机会点

三个变化让这件事现在可做：

1. **平台 API 成熟**：Amazon SP-API 的 Listings Items API / Feeds API 已支持程序化批量上架；Temu、Shopee、Lazada 均有开放平台；TikTok Shop 有 Seller API + 客服 API。
2. **AI 成本下降**：差评痛点归类、素材生成、客服分类、利润归因这些「非结构化 → 结构化」的活，LLM 做得又快又便宜。
3. **Codex 类工具**：可以显著提升代码实现、测试、重构和文档维护效率，但不能替代平台集成、财务、安全、法务与业务领域评审，也不能替代生产职责分离。

## 2. 产品定位与目标

### 2.1 定位

**一套自建、私有、可编排的跨境电商运营中台。**

不做 SaaS 卖给别人，做自己用。核心价值不是「功能多」，而是「串起来」：

```
选品 → 上架 → 素材 → 广告 → 库存 → 订单 → 客服 → 财务
  ↑                                                ↓
  └────────── 数据回流，反哺选品与定价 ←───────────┘
```

形成闭环，而不是 8 个孤岛工具。

### 2.2 产品目标（12 个月）

| 目标 | 量化指标 | 现状基线 |
|---|---|---|
| 降低重复人力 | 运营重复劳动时间下降 60% | 假设 6 小时/人/天 → 2.4 小时 |
| 缩短选品决策周期 | 候选品从发现到决策 < 3 天 | 行业基准 7 天 |
| 提升上架效率 | 单 SKU 上架耗时从 25 分钟降到 3 分钟 | 人肉填写 |
| 利润核算准确性 | 与平台实际结算差异 < 2% | 当前手工核算无法验证 |
| 竞品响应速度 | 竞品调价/活动 2 小时内预警 | 目前靠人肉周查 |
| 售后自动化率 | 60% 的售后咨询由系统自动回复或分类 | 0% |

### 2.3 非目标（明确不做）

避免范围蔓延，以下**不在本期范围**：

- ❌ 不做采购管理 / 供应商报价比价系统
- ❌ 不做自建海外仓 WMS（与第三方 WMS 对接即可）
- ❌ 不做自建物流轨迹系统（用平台 + 17TRACK 等）
- ❌ 不做 C 端独立站商城（Shopify 已有，只做数据对接）
- ❌ 不做直播、达人投放和广告投放执行；模板化商品视频仅作为 Phase 3 可选能力
- ❌ 不做法定会计总账、自动报税或法律/认证结论；只提供经营管理报表与风险线索
- ❌ MVP 不做自动退款、自动改价、自动调整广告预算、自动下架等高风险无人值守写操作

### 2.4 MVP 定义与规模边界

#### 2.4.1 默认 MVP（待业务方确认）

| 维度 | MVP 基线 | 后续扩展 |
|---|---|---|
| 平台 | Amazon | TikTok Shop、Temu、Shopee、Lazada、速卖通、Shopify、SHEIN |
| 区域 | 单一区域（NA/EU/FE 三选一） | 多区域统一管理 |
| 店铺 | 1-2 个授权店铺 | 多租户、多组织、多店铺 |
| 履约 | FBA | MFN、海外仓、平台半托管 |
| 商品规模 | 试点 20 SKU，稳定后扩至 100 SKU | 千级及以上 |
| 订单规模 | 以业务方近 90 天峰值 × 2 作为容量基线 | 水平扩容 |
| 数据能力 | 订单、库存、Listing、结算报告只读同步 | 广告、客服、竞品扩展 |
| 写能力 | 上架草稿生成；经人工审批后执行上架 | 改价、广告和售后写操作 |
| 报表 | 经营日报、库存预警、经营贡献利润、结算对账 | 周报、月报、选品与竞品报表 |
| AI | 标题/描述建议、消息分类建议，不自动对外发送 | 白名单自动回复、素材生成 |

#### 2.4.2 MVP 业务完成定义

MVP 只有在以下链路真实跑通后才算完成：

```text
授权店铺 → 增量同步订单/库存/Listing/结算数据
→ 生成上架草稿 → 人工审批 → 小批量上架
→ 平台结果回查 → SKU 映射校验
→ 经营贡献利润核算 → 结算对账 → 经营日报
```

任何单个页面或接口“开发完成”都不等于 MVP 完成。

### 2.5 版本能力矩阵

| 版本 | 核心范围 | 允许的自动化级别 | 退出条件 |
|---|---|---|---|
| Phase 0 基建 | 鉴权、数据模型、任务、审计、权限、通知 | 仅开发/沙箱 | 安全与架构评审通过 |
| Phase 1 MVP | Amazon 单区域主链路 | 只读自动；写操作人工审批 | 连续 14-30 天 Shadow + 财务对账通过 |
| Phase 2 数据智能 | 选品、广告归因、AI 建议、多平台第 2 个适配器 | 建议模式，不自动执行高风险动作 | 黄金集、成本和业务验收通过 |
| Phase 3 自动化 | 竞品、客服、素材、更多平台 | 白名单场景可自动；高风险仍审批 | 生产就绪评审通过 |
| Phase 4 规模化 | 多区域、多店铺、容量与成本优化 | 按风险等级逐步放权 | SLO 与错误预算稳定 |

**优先级解释**：P0/P1/P2 表示业务重要度，不直接等同于版本归属。每个验收标准必须同时标注适用版本，避免将最终愿景误当作 MVP 承诺。

## 3. 用户角色与场景

### 3.1 角色定义

| 角色 | 核心诉求 | 主要用到的模块 | 使用频率 |
|---|---|---|---|
| **老板 / 操盘手** | 一眼看到赚钱没、哪个品该砍、哪个品该追 | ⑤财务、⑦报表、⑧竞品监控 | 每日 1 次，看日报 |
| **选品专员** | 候选品清单 + 数据依据 + 评分 + 利润测算 | ①选品调研、⑦选品表输出 | 每周 2-3 次 |
| **运营** | 批量上架、商品信息、素材、库存预警 | ②上架、③素材、⑥平台对接、⑦库存预警 | 每日 |
| **客服** | 售后问题分类、回复建议、退换货处理 | ④客服售后 | 每日 |
| **财务** | 经营贡献利润、平台结算对账、费用归因 | ⑤财务 | 每周 / 每月 |
| **技术/SRE** | 系统稳定、任务可观测、故障可回滚 | 运维后台 | 按需 |
| **安全/法务** | 数据合规、权限边界、供应商与条款结论 | 运维后台、数据治理 | 按需 |

> 角色定义只描述职责与诉求；实际可执行动作由第 3.3 节 RBAC 权限矩阵决定。

### 3.2 关键用户旅程

**旅程 A：老板的早晨（8:30）**

```
打开飞书/企微 → 收到「经营日报」推送
  ↓
3 秒看懂：昨日销售额 / 履约后贡献利润 / 广告花费 / TACOS / 库存预警数 / 异常
  ↓
点开「异常详情」→ 发现 A 品库存仅够 6 天，且竞品刚降价 12%
  ↓
一键派单给运营 → 运营在系统里看到任务 + 建议动作（补货 / 跟价 / 暂停广告）
```

> 注：日报展示的是履约后贡献利润，不是会计净利润（见第 9.1 节会计边界）。

**旅程 B：选品专员的周一**

```
系统周一凌晨自动跑「选品巡检」→ 产出 30 个候选品，附评分卡
  ↓
专员打开选品看板 → 按评分排序 → 挑 8 个进入深度评估
  ↓
系统自动补全：经授权数据源的历史曲线、竞品差评痛点归类、利润模型测算、侵权风险线索
  ↓
专员确认 3 个进入测款 → 系统生成上架模板 + 素材需求单 → 流转到运营
```

**旅程 C：竞品突袭（实时）**

```
竞品 B 在 14:20 把主力款价格从 $29.99 调到 $24.99
  ↓
监控任务 14:25 抓到（核心竞品 5 分钟轮询；仅限已授权来源且预算允许）
  ↓
系统判断：跌幅 16.7% > 阈值 10%，且该 SKU 与我方 A 品直接对标
  ↓
14:26 推送预警给对应店铺值班人与负责人 + 给出建议：跟价到 $25.49 / 保持 / 加强广告
  ↓
运营决策后，系统生成变更单；仅在审批通过、限额校验通过且未触发 Kill Switch 时执行改价
```

### 3.3 RBAC 权限模型

权限按“组织 × 店铺 × 区域 × 资源 × 动作”授权，不允许仅按页面粗粒度控制。

| 角色 | 默认权限 | 明确禁止 |
|---|---|---|
| 老板/管理员 | 全局只读、审批高风险操作、查看经营汇总 | 直接读取明文 Token |
| 运营 | 管理授权店铺的商品、素材和上架草稿 | 越权查看其他店铺 PII；绕过审批改价/下架 |
| 客服 | 处理授权店铺消息和售后工单 | 导出全量买家数据；修改财务口径 |
| 财务 | 查看结算、成本、对账，维护经批准的成本规则 | 执行商品与客服写操作 |
| 技术/SRE | 系统运维、任务重跑、日志元数据 | 默认不得查看消息正文、买家信息和业务利润明细 |
| 审计员 | 只读查看审批与审计记录 | 发起或执行写操作 |

系统必须支持店铺级数据隔离、临时授权、授权到期、季度权限复核和离职即时回收。

### 3.4 审批矩阵与职责分离

| 操作 | 风险等级 | 默认审批 | 额外控制 |
|---|---|---|---|
| 上架草稿生成 | 低 | 无 | 只能生成草稿 |
| 批量上架/下架 | 高 | 运营发起 + 负责人审批 | 数量上限、幂等键、可取消窗口 |
| 改价 | 高 | 运营发起 + 负责人审批 | 最低毛利线、最大变动比例、冷静期 |
| 广告预算调整 | 高 | 运营发起 + 负责人审批 | 单日增量与账户预算上限 |
| 退款/补偿 | 高 | 客服发起 + 负责人或财务审批 | 金额分级、买家风险检查 |
| Token/密钥管理 | 极高 | 技术管理员双人复核 | 不展示明文、操作全审计 |
| 报表导出含 PII | 极高 | 数据 Owner 审批 | 水印、有效期、下载审计 |

审批记录至少包含：发起人、审批人、店铺、资源、操作前后值、规则版本、AI 建议及置信度、理由、金额/数量、过期时间、幂等键、执行结果和回滚结果。发起人与审批人不得为同一人。

### 3.5 审计、紧急停止与回滚

- 审计日志采用 append-only 设计，不允许业务用户修改或删除。
- 日志禁止记录明文 Token、密码、完整地址、买家消息全文等敏感信息。
- 对平台写操作提供全局、平台、店铺、能力四级 Kill Switch；触发后立即切换为只读。
- 支持 Break-glass 紧急访问，但必须限时、记录原因并在事后复核。
- “回滚”按平台能力区分：可逆操作执行补偿动作；不可逆操作只能停止后续执行并生成处置工单，禁止假设所有操作都可撤销。

### 4.1 八大模块关系图

```
                    └─────────────────────────────────────────┘
                                      ▲  ▼
   ┌──────────┬──────────┬──────────┬─┴────────┬──────────┬──────────┬──────────┬──────────┐
   │ ①选品调研 │ ②商品上架 │ ③素材生成 │ ④客服售后 │ ⑤财务核算 │ ⑥平台对接 │ ⑦报表输出 │ ⑧竞品监控 │
   └──────────┴──────────┴──────────┴──────────┴──────────┴──────────┴──────────┴──────────┘
        │          │           │          │          │          │          │          │
        └──────────┴───────────┴──────────┴──────────┴──────────┴──────────┴──────────┘
                                      │
                    ┌─────────────────┴─────────────────┐
                    │   编排层：Celery Beat（MVP）        │
                    │   定时任务 · 依赖调度 · 失败重试     │
                    └─────────────────┬─────────────────┘
                                      │
                    ┌─────────────────┴─────────────────┐
                    │  AI 层：LLM 网关（多模型路由）       │
                    │  分析 · 归类 · 生成 · 归因          │
                    └─────────────────┬─────────────────┘
                                      │

                    │  交互层：Web 后台 + 企微/飞书机器人  │
                    └───────────────────────────────────┘
```

### 4.2 闭环数据流（核心）

这是整套系统的灵魂 —— **数据必须回流**：

```
① 选品 → 输出「选品表 + 上架模板」
            ↓
② 上架 → 商品在平台上线，产生 SKU 映射
            ↓
③ 素材 → 为上架商品生成主图/详情/A+ 素材
            ↓
⑥ 平台对接 → 持续拉回：订单、库存、广告、结算、评价
            ↓
⑤ 财务 → 用真实结算数据核算利润，反哺选品利润模型校准
            ↓
④ 客服 → 售后问题归类，反哺选品的「产品改进清单」
            ↓
⑧ 竞品监控 → 价格/活动/排名/评论异常，触发定价与广告调整
            ↓
⑦ 报表 → 所有数据汇总成报表，输出给决策者
            ↓
回到 ①：用真实利润数据 + 售后痛点 + 竞品动态，重新校准选品评分模型
```

**关键设计原则**：任何模块都不是终点，都要往上游输送数据。比如客服模块不只回复客户，还要把「哪个卖点被投诉最多」输出给选品和素材模块。

# 第二部分：八大模块详细需求

## 5. 模块① 选品调研自动化

### 5.1 模块目标

把「选品」从依赖个人经验的模糊判断，变成**有数据依据、有评分标准、可复盘**的流水线。

### 5.2 功能需求

#### F1.1 趋势发现（三层数据漏斗的第一层）

| 需求项 | 说明 | 优先级 |
|---|---|---|
| 趋势数据采集 | 优先使用已获授权的 Google Trends API Alpha 或经批准的数据服务；未获权限时采用人工导入，不阻断 MVP。同步平台榜单须逐源确认授权与条款 | P0 |
| 品类生命周期辅助判断 | 综合 3-5 年趋势、平台销量、价格和供给变化输出阶段判断、置信度与依据，不自动作为最终结论 | P0 |
| 季节性识别 | 至少使用 24-36 个月数据识别周期性；只有 12 个月数据时必须标记低置信并人工复核 | P0 |
| 区域对比 | 同品类在不同站点的搜索热度对比，选目标市场 | P1 |
| 上升词挖掘 | 提取「相关查询」中的上升词，发现细分需求 | P1 |

#### F1.2 平台数据深挖（第二层）

| 需求项 | 说明 | 优先级 |
|---|---|---|
| 市场容量测算 | 细分市场月销量、销售额规模 | P0 |
| 竞争强度评估 | 头部集中度（Top10 销量占比）、新品存活率、广告密度（核心词 CPC） | P0 |
| 历史曲线证伪 | 对接 Keepa 类数据，排除刷单尖刺、识别新品爬升速度 | P0 |
| 关键词反查 | 还原竞品流量入口结构，识别高价值词 | P1 |
| 价格带分析 | 类目价格分布，找到价格空白区 | P1 |
| 评论痛点挖掘 | 抓取竞品 1-3 星评论，LLM 归类痛点 → 产品改进清单 | P0 |

#### F1.3 跨平台验证（第三层）

| 需求项 | 说明 | 优先级 |
|---|---|---|
| 品牌格局分析 | 类目内品牌年销售额、产品线、流量结构 | P1 |
| 多渠道比价 | 同一候选品在 Amazon/eBay/Walmart 的销量、均价、竞争度 | P1 |
| 独立站流量验证 | 竞品独立站流量规模与渠道构成 | P2 |
| 侵权风险线索 | 商标/专利/外观检索仅输出风险线索、来源和置信度，不构成法律结论；高风险候选必须经法务/知识产权顾问复核 | P0 |
| 合规要求提示 | 目标市场认证要求（如 FCC/CE/CPSC）自动提示并附来源；是否满足要求由合规负责人确认 | P0 |

#### F1.4 选品评分卡（系统核心算法）

八维度加权评分，**阈值可配置、权重可调、每次决策留痕**：

| 维度 | 默认权重 | 数据来源 | 及格线 |
|---|---|---|---|
| 市场需求规模 | 20% | 月销量估算 | 细分市场月销 ≥ 1 万件 |
| 趋势健康度 | 15% | 12 个月趋势曲线 | 上升或平稳，非衰退期 |
| 竞争强度 | 20% | 头部集中度 / 评论规模 | Top10 不占 80% 销量 |
| 利润空间 | 15% | 利润模型（含退货与广告） | 毛利率 ≥ 35% |
| 差异化空间 | 10% | 差评痛点密度 | ≥ 3 个可改进痛点 |
| 供应链可行性 | 10% | 交期/起订量/柔性产能 | 交期 ≤ 30 天，可小单起订 |
| 合规风险 | 5% | 商标专利筛查 | 无侵权记录、认证可达 |
| 复购与延展性 | 5% | 品类复购率/关联购买 | 有耗材或系列化空间 |

**决策规则**：加权总分 ≥ 80 进入测款名单；60-80 观察；< 60 淘汰。

#### F1.5 数据交叉验证机制

**这是选品质量的关键保障**：

- 同一指标（如月销量）在不同数据源可能出现显著差异，系统必须支持**多源采集 + 来源版本 + 差异标注**。
- 至少两个可比数据源存在时才计算源间偏差；偏差超过 25% 标记“低置信度”。
- 只有单一数据源时默认标记“单源、低置信度”，不得伪造差异值。
- 重大决策（备货 > 1 个月预计销量）强制要求至少两个独立来源，或由业务负责人书面批准例外。

### 5.3 选品巡检任务（自动化流程）

```
每周一 02:00 自动触发
  ↓
Step 1  拉取各平台榜单 + 趋势数据（接口 + 采集）
Step 2  按预设筛选条件粗筛（月销、价格带、评论数区间）
Step 3  对候选品批量补充：Keepa 曲线、关键词、竞品评论
Step 4  LLM 分析：差评痛点归类、卖点提炼、差异化建议
Step 5  利润模型测算（含头程/佣金/退货/广告）
Step 6  侵权与合规初筛
Step 7  计算评分卡，排序
Step 8  输出《选品周报》+ 候选品清单 → 推送企微/飞书 + 落库
  ↓
人工终审：选品专员在 Web 后台逐个确认/否决，填写理由
  ↓
系统记录决策留痕 → 用于后续校准评分模型
```

### 5.4 验收标准

- [ ] 单次巡检可产出 ≥ 50 个候选品，覆盖 ≥ 3 个平台
- [ ] 每个候选品至少包含 6 项数据依据（销量、趋势、竞争、利润、痛点、合规）
- [ ] 评分卡计算不依赖人工干预，全自动完成
- [ ] 决策留痕可追溯：任一历史选品决策能还原当时的全部数据依据
- [ ] 多源数据差异自动标注置信度

## 6. 模块② 商品上架自动化

### 6.1 模块目标

在类目 schema、合规资料和素材已齐备的前提下，将单 SKU 的人工录入时间显著降低。具体目标由 MVP 基线测试确定；平台异步审核时间不计入系统处理时间，也不承诺所有类目或变体结构达到同一效率。

### 6.2 平台 API 对接方案

#### F2.1 Amazon（SP-API）

| 能力 | API | 说明 |
|---|---|---|
| 判断商品是否已在目录 | `Catalog Items API (2022-04-01)` | 先搜，避免重复创建 |
| 获取商品类型属性要求 | `Product Type Definitions API (2020-09-01)` | 不同类目必填字段不同，必须动态获取 schema |
| 检查上架限制 | `Listings Restrictions API (2021-08-01)` | 类目是否需要审批、是否受限 |
| 单个创建/更新 | `Listings Items API (2021-08-01)` | JSON 结构，适合精细控制 |
| 批量创建/更新 | `Feeds API (2021-06-30)` | 大批量走 Feeds，基于 JSON 上传 |
| 状态订阅 | `Notifications API` | 订阅 Listing 状态变化，实时知道上架成功/失败 |
| 结果核对 | `Reports API`（All Listings Report） | 定期拉全量 Listing 报告对账 |

**关键约束（必须写进设计）**：

- **限流**：Listings Items API 有严格速率限制，批量必须走 Feeds + 队列，加指数退避
- **属性动态性**：不能硬编码属性字段，必须每次拉 Product Type Definition 生成表单
- **异步确认**：Feeds 提交是异步的，必须轮询 processingReport 确认结果，不能提交即认为成功
- **图片规范**：主图纯白底、尺寸要求等由类目决定，素材模块要按规范产出

#### F2.2 TikTok Shop

- 走 TikTok Shop Seller API（需申请开发者 + 卖家授权）
- 商品发布接口、库存同步、订单拉取
- **注意**：客服 API 需特别审批，读取店铺数据须先取得该卖家授权

#### F2.3 Temu

- 以 Temu Partner Platform 的官方 Developer Guide、API Reference、Seller Authorization Guide 和数据安全政策为实施依据。
- 官方文档明确支持卖家在 Seller Center 中手动授权应用并选择权限；不同主体、区域和合作模式必须分别核验 Partner Platform 入口及授权范围。
- 第三方文章所称“预备金约 1 万元”“全托管上新 ≥100 件”等商务门槛属于**待验证假设**，不得作为架构硬约束；签约前由商务 Owner 取得官方书面规则并登记到第 21.5 节。
- Token、店铺、区域和权限范围必须绑定存储，禁止跨店铺或跨区域复用；具体隔离方式以授权响应和官方文档为准。
- 商品、库存、订单、价格与 Webhook 能力以实际获批权限为准，未获批能力必须降级为文件导入或人工操作。

#### F2.4 Shopee / Lazada / 速卖通

- Shopee Open Platform：OAuth 授权，商品/订单/物流 API 齐全
- Lazada Open Platform：类似 Shopee，需申请 App Key
- 速卖通（AliExpress）：阿里开放平台，商品发布 API 完善

#### F2.5 Shopify 独立站

- Admin API（GraphQL）创建/更新商品，支持批量
- 与选品模块联动：选中品可直接推送到 Shopify 草稿

### 6.3 功能需求

| 需求项 | 说明 | 优先级 |
|---|---|---|
| 上架模板生成 | 按平台 + 类目动态生成上架 Excel/JSON 模板，预填已知字段 | P0 |
| 批量导入校验 | 导入前校验必填项、字符数限制、图片规范、禁售词 | P0 |

### 7.1 模块目标

按平台规范批量产出主图、场景图、详情页、A+ 素材、短视频，把「等设计师」变成「系统直出 + 人工挑选」。

| 需求项 | 说明 | 优先级 |
|---|---|---|
| 白底主图 | 抠图 + 纯白底 + 平台尺寸规范 | P0 |
| 场景图生成 | 基于产品图 + 场景描述，AI 生成使用场景图 | P0 |
| 卖点图/信息图 | 模板化：产品图 + 卖点文案 + 排版 | P0 |
| 尺寸对比图 | 自动生成尺寸标注图 | P1 |
| 详情页长图 | 按平台规范拼接：卖点 + 场景 + 参数 + 对比 | P0 |
| A+ 页面素材 | Amazon A+ 模块化素材（标准 5 模块 / 高级模块） | P1 |
| 模板化商品视频 | 产品图 → 图集视频 / 简单动效视频，仅作为 Phase 3 可选能力；不包含直播、达人内容和广告投放 | P2 |
| 多语言版本 | 按目标站点自动翻译文案并重新排版图文 | P1 |
| 素材合规检查 | 尺寸、格式、白底比例、文字占位、禁用元素检查 | P0 |

| 批量任务 | 一次提交 N 个 SKU × M 种素材类型，队列执行 | P0 |

### 7.3 关键规范（必须内置）

不同平台/类目的素材规范差异极大，必须做成**可配置规则库**而不是硬编码：

| 平台 | 主图 | 附加要求 |
|---|---|---|
| Amazon | 纯白底 RGB(255,255,255)，最长边 ≥ 1600px（支持缩放），产品占图 ≥ 85% | 主图不能有文字/水印/边框；附图可使用场景图 |
| TikTok Shop | 建议 1:1，≥ 800×800 | 首图需清晰无文字遮挡 |
| Temu | 1:1 白底为主 | 有严格的图片质量审核 |
| Shopee | 1:1，≥ 500×500 | 首图白底优先 |

### 7.4 技术方案要点

- **抠图**：优先用本地模型（如 RMBG / SAM 系列）批量处理，成本可控；复杂图走云端 API
- **生成**：文生图/图生图（ImageGen 类能力），提示词模板化，由 LLM 根据产品信息生成提示词
- **排版**：用 PIL / Pillow 或 HTML→图片渲染（Playwright），模板可配置
- **质量控制**：生成后自动跑一遍「明确性检查」（尺寸、白底、清晰度、文字占比），不合格打回重生成
- **成本控制**：优先本地处理，AI 生成部分做缓存与去重，避免同一产品重复扣费

### 7.5 验收标准

- [ ] 单 SKU 可一键生成：1 张白底主图 + 3 张场景图 + 1 张卖点图 + 1 张详情长图
- [ ] 在指定硬件/API 配额下，以“100 SKU × 每 SKU 6 张图、最长边 1600px、不含人工审核”为基准建立性能基线；目标由 PoC 实测后写入 SLO，禁止使用“视算力”作为验收口径。
- [ ] 自动合规检查拦截率 ≥ 90%（不合格素材不进上架流程）
- [ ] 素材与 SKU 强绑定，可在素材库按 SKU 检索全部版本

| 退货率监控 | 按 SKU 监控退货率，超阈值预警 | P0 |

### 8.3 技术难点与对策

| 难点 | 对策 |
|---|---|
| 平台客服 API 权限与能力差异 | TikTok Shop 官方说明要求卖家授权第三方系统获取客服数据；Amazon Messaging API 不应被视为通用历史消息读取 API。**降级方案**：受控邮件接入、平台导出文件或人工工作台 |
| 多语言语义准确 | 用多语言 LLM + 术语表（产品专有名词保护），按语言与意图分层评测，关键类目人工抽检 |
| 自动回复风险 | Phase 1 仅生成建议回复并由人工发送；后续只有白名单意图、低金额且高置信场景可自动回复。涉钱、法律承诺、差评、平台纠纷一律转人工 |
| 分类准确性 | 建立标注集，持续评估；分类结果人工可纠正，纠正数据回流训练/提示优化 |

### 8.4 验收标准

- [ ] 在不少于 1,000 条、覆盖主要语言和意图的冻结黄金集上，宏平均 F1 ≥ 0.85；高风险意图召回率 ≥ 0.98。

- [ ] Phase 1 只验证建议回复质量；自动回复率不作为 MVP 指标。
- [ ] 客服数据按最小必要字段结构化落库；消息正文和 PII 遵循第 15.4 节保留与删除要求。
- [ ] 高频问题自动产出改进清单，每周推送；人工纠正结果进入评测数据闭环。

## 9. 模块⑤ 财务利润核算自动化

### 9.1 模块目标与会计边界

算清楚每个 SKU、店铺和站点的**经营贡献利润**，并与平台结算做可解释对账。本模块属于管理报表，不替代法定会计总账、税务申报或审计结论；需要法定财务结果时，应与现有财务/ERP 系统对接。

“误差 <2%”只可用于已定义范围内的结算金额对账，不可笼统表示完整会计利润准确性。

### 9.2 功能需求

#### F5.1 成本项全量采集

| 成本项 | 数据来源 | 说明 |
|---|---|---|
| 采购成本 | 内部录入 / ERP | 含税、含包装 |
| 头程物流 | 货代账单 / 手工录入 | 按重量或体积分摊 |
| 平台佣金 | 平台结算报告 | Amazon Referral Fee 等 |
| FBA 费用 | Amazon FBA Fee Report | 仓储费 + 配送费 + 长期仓储 |
| 广告费 | 广告 API 报表 | 按 SKU/Campaign 归因 |
| 退货成本 | 客服模块 | 退货处理费 + 损失 |
| 汇率损失 | 结算报告 | 结算汇率 vs 记账汇率差异 |
| 税费 | VAT / 销售税报告 | 欧洲站点必须 |
| 其他 | 人工补充 | 促销费、优惠券、合作达人佣金 |

#### F5.2 经营贡献利润模型

```text
净销售额 = 商品销售额 + 买家承担运费 - 折扣 - 退款 - 拒付 - 销售相关税费（按既定口径）
履约前贡献利润 = 净销售额 - 商品销售成本 - 头程分摊
履约后贡献利润 = 履约前贡献利润 - 平台佣金 - 配送/仓储费 - 退货处理及不可售损失
广告后贡献利润 = 履约后贡献利润 - 可归因广告费 - 促销/达人佣金 - 其他可变费用

关键派生指标：
- 履约后贡献毛利率 = 履约后贡献利润 / 净销售额
- 广告后贡献利润率 = 广告后贡献利润 / 净销售额
- TACOS = 广告费 / 净销售额（全系统统一采用净销售额作为分母）
- 单件广告后贡献利润 = 广告后贡献利润 / 已结算销量
- 保本 ROAS = 1 / 广告前可投放贡献毛利率，仅在广告是唯一新增可变成本时成立
- 库存周转天数 = 平均库存成本 / 日均销货成本
```

“净利润”一词仅在已纳入人工、租金、折旧、管理费、融资成本等完整期间费用并经财务负责人确认时使用；否则统一称为“贡献利润”。

#### F5.2.1 四类报表必须分开

| 报表 | 时间口径 | 目的 |
|---|---|---|
| 订单经营视图 | 下单时间 | 日常运营趋势，不代表最终结算 |
| 履约贡献利润 | 发货/完成时间 | SKU 和渠道经营决策 |
| 平台结算对账 | 结算批次时间 | 核对平台实际收付款与费用 |
| 会计报表 | 会计期间 | 由外部财务系统负责，本系统只提供凭证和对接数据 |

#### F5.2.2 归因与关账政策

- 库存成本计价采用移动加权或 FIFO，立项时由财务 Owner 二选一并锁定版本。
- 头程按实际计费重、体积重或件数分摊；分摊规则必须版本化并可追溯。
- 广告无法直接归因到 SKU 时进入“待分摊池”，不得静默平均分摊。
- 汇率同时记录交易日汇率、结算汇率和记账汇率；实现与未实现汇兑差额分开。
- 月度关账后数据冻结；任何追溯调整需创建调整单，不直接覆盖历史快照。
- 税费按含税/不含税口径分别存储；平台代征税、VAT、销售税不得混为一个字段。

#### F5.3 功能清单

| 需求项 | 说明 | 优先级 |
|---|---|---|
| 结算报告拉取 | 定时拉取各平台结算/交易报告 | P0 |
| 成本项维护 | 采购、头程、其他费用的录入与批量导入 | P0 |
| 费用自动归因 | 平台费用按 SKU / 订单自动归因 | P0 |
| 广告费归因 | 广告费按 SKU / Campaign / 关键词归因 | P0 |
| 汇率管理 | 多币种，按结算日汇率换算，可手工锁定 | P0 |
| 多维度利润表 | 按 SKU / 店铺 / 站点 / 类目 / 时间维度 | P0 |
| 利润趋势 | 日/周/月利润趋势与环比同比 | P0 |
| 异常利润预警 | 某 SKU 利润骤降/转负自动预警 | P0 |
| 对账功能 | 系统核算 vs 平台实际结算差异比对 | P1 |
| 库存资金占用 | 库存成本、资金占用天数、周转率 | P1 |
| 现金流视图 | 平台回款周期 + 应付账期 → 现金流预测 | P2 |
| 成本模型校准 | 用实际结算数据反校准选品的利润模型 | P0 |

#### F5.4 关键设计：算得准的三个前提

1. **归因要准**：广告费、退货费必须能落到具体 SKU，否则利润表就是糊的
2. **时间口径统一**：按下单时间还是结算时间？系统必须固定一种并全站一致（建议：经营视角按下单时间，财务对账按结算时间，两套并列）
3. **汇率口径明确**：结算汇率、记账汇率分开记录，差异单独列示

### 9.3 验收标准

- [ ] Phase 1 支持 Amazon 单区域结算报告；≥5 平台属于 Phase 4 愿景。
- [ ] 至少选择两个已关闭结算周期完成对账；分别报告金额差异率、笔数差异、未匹配项和时间性差异。
- [ ] 已匹配结算金额差异率 <2%；所有差异必须能下钻到订单、费用代码或汇率记录。
- [ ] 任一 SKU 可下钻查看成本构成、规则版本、来源和关账状态。
- [ ] 利润异常预警在不少于 30 天历史回放上达到 Precision ≥0.90，并设置最小金额门槛防止小额噪音。
- [ ] 财务 Owner 签字确认指标字典、成本计价、分摊和关账政策后，成本模型方可反哺选品。

## 10. 模块⑥ 跨境电商平台对接

### 10.1 模块目标

用一套统一的内部数据模型，屏蔽各平台差异，让上层模块（选品/上架/财务/客服）只面对一种数据结构。

### 10.2 统一抽象层设计（核心）

```
                  ┌──────────────────────────────────┐
                  │   统一电商中台数据模型（内部标准）  │
                  │  Product / Order / Inventory      │
                  │  Ads / Customer / Finance         │
                  └──────────────┬───────────────────┘
                                 │ 适配器（Adapter）
     ┌───────────┬───────────┬───┴───────┬───────────┬───────────┐
     │  Amazon   │ TikTok    │   Temu    │  Shopee   │  Shopify  │
     │  Adapter  │ Adapter   │  Adapter  │  Adapter  │  Adapter  │
     └───────────┴───────────┴───────────┴───────────┴───────────┘
```

**平台能力并不对称，适配器不得强迫平台实现不存在的接口。** 每个适配器先声明能力，再按能力调用：

```python
class Capability(str, Enum):
    NATIVE = "native"          # 官方 API 直接支持
    ASYNC = "async"            # 异步任务/Feed/报表
    WEBHOOK = "webhook"        # 平台事件推送
    FILE_IMPORT = "file_import"# 官方导出文件导入
    MANUAL = "manual"          # 仅人工流程
    UNSUPPORTED = "unsupported"# 当前不可用

class PlatformAdapter(ABC):
    def capabilities(self) -> dict[str, Capability]: ...
    def authorize(self, shop_id: str) -> Token: ...
    def refresh_token(self, shop_id: str) -> Token: ...
    def health_check(self, shop_id: str) -> HealthStatus: ...

    def pull_incremental(self, resource: str, cursor: Cursor) -> Page: ...
    def submit_command(self, command: PlatformCommand) -> Submission: ...
    def poll_submission(self, submission_id: str) -> SubmissionStatus: ...
    def import_official_file(self, resource: str, file_ref: str) -> ImportResult: ...
```

统一命令对象应包含 `tenant_id`、`shop_id`、`idempotency_key`、`requested_by`、`approved_by`、`rule_version` 和 `dry_run`。所有适配器必须返回统一错误分类：鉴权、限流、校验、权限不足、资源不存在、暂时性平台错误、永久性业务错误和未知错误。

### 10.2.1 能力矩阵（接入前必填）

每个平台、区域、店铺类型必须单独维护能力矩阵，不得用“接口完整”概括：

| 能力 | Amazon MVP | 其他平台接入时 |
|---|---|---|
| 商品读取 | 以官方 API/报告核验结果登记 | 标记 native/async/file/manual/unsupported |
| 商品创建/更新 | Listings Items 或 JSON Feed，异步确认 | 同上 |
| 订单读取 | 官方 API，受权限与 PII 角色限制 | 同上 |
| 库存读取/更新 | 按履约模式核验 | 同上 |
| 广告报表 | 独立 Ads API 授权 | 同上 |
| 客服消息读取 | 不假定支持通用历史消息读取 | 同上 |
| 结算/费用 | 报告或交易接口 | 同上 |
| Webhook/通知 | 可用则订阅，但不能作为唯一对账来源 | 同上 |

### 10.2.2 同步协议、幂等与补数

- 每个资源维护增量游标/水位、最后成功时间、最后完整核对时间和时区。
- 原始平台报文加密后不可变归档，规范化数据记录来源报文哈希与转换版本，支持重放。
- Webhook 只作为触发信号，定期全量或报告对账作为最终一致性保障。
- 分页、延迟到达、删除、状态反转、部分成功和重复消息必须有契约测试。
- 写操作必须支持 dry-run、幂等键、审批校验、限额、超时和补偿动作。
- 补数必须指定平台、店铺、资源、时间窗口和原因，不允许无边界全量重跑。

### 10.2.3 API 版本与降级策略

- 每个适配器登记 API 版本、官方文档链接、Owner、最后核验日期和预计退役日期。
- 每日或每周监测废弃公告；重大版本升级必须经过契约测试与沙箱/小流量验证。
- 外部依赖不可用时，按顺序降级：暂停写入 → 只读旧数据并标记新鲜度 → 官方文件导入 → 人工处理。
- 不得因追求数据新鲜度而绕过平台条款、权限或速率限制。

### 10.3 功能需求

| 需求项 | 说明 | 优先级 |
|---|---|---|
| 多店铺管理 | 一个平台可绑定多店铺，多站点 | P0 |
| 授权管理 | OAuth / Token 全流程，含刷新与失效检测 | P0 |
| Token 巡检 | 定时检查 token 有效期，过期前 7 天提醒 | P0 |
| Token 加密存储 | 数据库加密存储，禁止明文 | P0 |
| 统一限流器 | 按平台/接口维度限流，防止被封 | P0 |
| 失败重试 | 指数退避 + 抖动，区分可重试/不可重试错误 | P0 |

| 接口日志 | 仅记录字段白名单、状态码、请求 ID、耗时和脱敏摘要；敏感报文采用受控短期采样，禁止默认全量记录 Token/PII | P0 |

### 10.4 各平台对接要点清单

| 平台 | 认证方式 | 关键注意 |
|---|---|---|
| Amazon | LWA OAuth 2.0 | 区域 Base URL 必须匹配（NA/EU/FE）；refresh_token 长期有效需加密 |

- [ ] 每个平台未支持的能力显式标记为 unsupported/manual/file_import，不允许静默失败。

| 指标口径管理 | 所有指标有唯一定义，避免口径打架 | P0 |
| 数据下钻 | 报表数字可点击下钻到明细 | P1 |

### 11.4 关键设计：指标口径统一

**这是报表模块最容易被忽视但最重要的事**。必须建立「指标字典」，每个指标有唯一 ID、明确计算公式、数据来源、负责模块：

| 指标 | 公式 | 数据来源 |
|---|---|---|
| GMV | Σ 订单金额（下单口径，未扣退款） | 订单表 |
| 净销售额 | GMV - 退款 - 折扣 | 订单表 + 财务 |
| 毛利 | 净销售额 - 采购 - 头程 - 平台佣金 - FBA - 退货成本 | 财务模块 |
| 净利 | 毛利 - 广告 - 税 - 汇率损失 - 其他分摊 | 财务模块 |
| TACOS | 广告费 / 净销售额 | 广告 + 财务 |
| 履约后贡献毛利率 | 履约后贡献利润 / 净销售额 | 财务模块 |
| 广告后贡献利润率 | 广告后贡献利润 / 净销售额 | 财务模块 |
| 库存周转天数 | 平均库存成本 / 日均销货成本（金额口径，全系统唯一） | 库存 + 财务 |

**口径一致性规则**：TACOS 分母全系统统一为净销售额，禁止在不同报表混用广告销售额或 GMV 作为分母；库存周转天数统一采用金额口径，数量口径如确有需要必须命名为“库存周转次数（数量口径）”并单独登记。

### 11.5 验收标准

- [ ] 所有报表可定时自动生成并推送，无人工干预
- [ ] 报表生成失败自动重试并告警
- [ ] 指标口径字典完整，所有报表数字可溯源到公式
- [ ] 图片卡片在手机端可清晰阅读
- [ ] 历史报表保留 ≥ 24 个月，可检索

## 12. 模块⑧ 竞品监控与定时任务自动化

### 12.1 模块目标

把「人肉定期看竞品」变成「系统 7×24 盯着，异常才叫人」。

### 12.2 监控维度

| 维度 | 监控内容 | 轮询粒度 | 预警阈值（可配置） |
|---|---|---|---|
| **价格** | 竞品售价、促销价、优惠券、Prime 折扣 | 5-30 分钟 | 变动幅度 > 5% 或 > 10%（分档） |
| **活动** | 是否上活动、Deal 类型、活动时长、Banner 变化 | 1-6 小时 | 命中活动即预警 |
| **排名** | BSR 大类/小类排名、关键词排名 | 1-6 小时 | 排名变动 > 20% 或进入/跌出 Top N |
| **评论** | 评论数、评分、新增评论内容、差评 | 1-6 小时 | 短时间差评激增（如 24h 内 ≥ 3 条 1-2 星） |
| **库存** | 竞品是否断货、库存水位推断 | 1-6 小时 | 断货 / 疑似补货 |
| **Listing 变更** | 标题、主图、卖点、A+ 变更 | 每日 | 任何核心要素变更 |
| **广告位** | 竞品是否投我方核心词 | 每日 | 新出现广告位 |
| **销量估算** | 基于经授权数据源的排名/销量模型推算，必须展示置信度 | 每日 | 销量异动 > 30% |

### 12.2.1 数据来源与许可矩阵

竞品监控不是默认允许的“爬虫项目”。每个来源必须经过数据 Owner 与法务确认：

| 来源类型 | 默认策略 | 必备记录 |
|---|---|---|
| 官方 API / Webhook | 优先 | 应用权限、速率限制、数据用途和保留要求 |
| 已授权数据服务商 | 可用 | 合同、API 许可、地域覆盖、SLA、数据再分发限制 |
| 平台官方导出文件 | 可用 | 导出人、时间、文件哈希、字段版本 |
| 公开网页采集 | 最后手段，需书面批准 | 服务条款、robots、版权/数据库权利评估、地区、登录态、频率和法务结论 |
| 绕过限制的账号、代理或验证码方案 | 禁止 | 不得实施 |

达到平台限制、出现验证码、访问被拒或条款变化时，系统必须自动降频、停采或切换到授权数据源，不得通过多账号或代理规避限制。

### 12.2.2 采集容量与成本模型

- 为每个来源设置每分钟、每日和每月调用预算，以及并发、重试和页面配额。
- 跟踪“每千次调用成本、每竞品/日成本、每有效告警成本、误报处理成本”。
- 设置月度费用熔断线；达到 80% 告警，达到 100% 停止非关键采集。
- 每次采集记录地区、币种、时间、页面/接口版本、原始证据哈希和置信度，避免跨地区价格误判。
- 5-30 分钟轮询仅适用于已授权且预算允许的核心竞品；其他对象采用小时/日级或事件驱动。

### 12.3 定时任务体系

**任务分层设计**：

| 层级 | 频率 | 任务 |
|---|---|---|
| **实时层** | 5-15 分钟 | 核心竞品价格、我方库存安全线、订单异常 |
| **小时层** | 1-6 小时 | 竞品排名/评论/活动、平台数据同步增量 |
| **日层** | 每日 | 竞品全量巡检、日报生成、库存预警、售后统计、订单对账 |
| **周层** | 每周 | 选品巡检、竞品深度分析、利润报表、周报 |
| **月层** | 每月 | 月报、成本模型校准、评分卡权重复盘、数据归档 |

**任务编排要求**：

- **依赖管理**：任务间有依赖（如日报依赖数据同步完成），必须支持 DAG 编排
- **失败重试**：区分瞬时错误（重试）与逻辑错误（告警不重试）
- **幂等性**：任务重复执行结果一致
- **超时控制**：每个任务有超时上限，超时即中断并告警
- **可观测**：每个任务的执行历史、耗时、成功失败率可查
- **手动触发**：支持后台手动重跑任意任务
- **回滚/补数**：支持指定日期补跑历史数据

### 12.4 预警机制

**三级预警**：

| 级别 | 触发条件 | 通知方式 | 响应要求 |
|---|---|---|---|
| P0 紧急 | 竞品降价 > 15% 且直接影响主力款；断货风险 < 3 天；差评激增；授权失效 | 仅通知对应店铺值班人与负责人，超时按升级策略通知；必要时短信 | 1 小时内响应 |
| 🟠 P1 重要 | 竞品价格变动 5-15%；排名变动 > 20%；利润转负；退货率超阈值 | 企微/飞书群消息 | 当日响应 |
| 🔵 P2 提示 | 一般变动、趋势提示 | 日报汇总 | 周内关注 |

**预警必须带「建议动作」**，而不是只报警：

```
【价格预警】竞品 B 主力款 X
当前价 $24.99（原 $29.99，↓16.7%），变动时间 14:20
影响：与我方 A 品（$29.99）直接对标，历史价格弹性 -1.2
建议：
  方案一 跟价至 $25.49（保住 Buy Box，毛利率降至 32%，仍高于 30% 红线）
  方案二 维持价格，加强广告（预算 +30%，预计 ACOS 上升 4%）
  方案三 保持观察 24h（若竞品 24h 内恢复原价则不动）
[一键执行跟价]  [查看竞品历史]  [忽略]
```

### 12.5 售后问题分类与退换货自动化

（与模块④协同，此处侧重自动化流程编排）

```
退货申请到达
  ↓
Step 1  自动判断：是否在退货窗口内？金额是否低于阈值？买家历史退货率？
  ↓
Step 2  规则判定
        ├─ 低风险（窗口内 + 金额小 + 原因合理）→ 自动通过 → 通知仓库 → 记财务
        ├─ 中风险 → 生成处理建议 → 人工一键确认
        └─ 高风险（高频退货买家/金额大/原因异常/疑似欺诈）→ 强制人工 + 标记
  ↓
Step 3  退货原因归类（LLM）→ 落库 → 计入 SKU 退货率
  ↓
Step 4  若某 SKU 退货率 > 阈值 → 触发预警 + 生成改进任务 → 推给选品/产品
  ↓
Step 5  退款执行（API 或人工确认）
  ↓
Step 6  退货成本计入财务模块
```

### 12.6 验收标准

- [ ] 核心竞品价格变动可在 30 分钟内捕获（视轮询粒度）
- [ ] 预警准确率 ≥ 85%（无大量噪音骚扰）
- [ ] 每条预警都带建议动作，运营可直接执行
- [ ] 定时任务失败率 < 1%，且失败可自动重试或告警
- [ ] 支持按日期补数，任务可手动重跑
- [ ] 退换货自动化率 ≥ 40%（低风险单自动处理）

# 第三部分：技术方案

## 14. 技术架构

### 14.1 技术选型（及理由）

| 层次 | 选型 | 理由 |
|---|---|---|
| 语言 | Python 3.12+ | 爬虫生态、数据处理、AI 集成都是最成熟的；团队上手快 |
| Web 框架 | FastAPI | 异步性能好，自动生成 API 文档，类型提示友好（对 Codex 生成代码也友好） |
| 主数据库 | PostgreSQL 16 | JSONB 适合存平台异构数据；窗口函数适合做报表；分区表适合大量订单 |
| 缓存/队列 | Redis | 缓存 + Celery broker + 分布式锁 + 限流计数 |
| 任务队列 | Celery + Celery Beat | 生态成熟，适合中小规模定时任务 |
| 工作流编排 | MVP 仅用 Celery Canvas + 状态表；达到迁移触发条件后再评估 Temporal | MVP 禁止同时维护两套编排语义。触发条件：跨天长流程、多级人工等待、补偿事务或 Celery 可观测性无法满足 SLO |
| 对象存储 | MinIO（自建）/ 阿里云 OSS | 素材、报表、归档文件 |
| 前端 | Vue 3 + Vite + Element Plus | 上手快，组件库全，适合内部后台 |
| 容器化 | Docker Compose → K8s（后期） | 先单机 Compose，规模上来再上 K8s |
| 监控 | Prometheus + Grafana + Loki | 指标 + 日志 + 告警 |
| AI | LLM 网关（多模型路由） | 不同任务用不同模型，成本与效果平衡 |

### 14.2 为什么不用现成的 n8n / 低代码

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| n8n / 低代码编排 | 上手快，画流程图 | 复杂业务逻辑难表达；调试困难；平台 API 的复杂签名/限流难处理；数据模型受限于节点 | ❌ 不适合做核心业务系统 |
| 纯自研 Python | 完全可控，调试方便，逻辑复杂也不怕 | 开发量大 | ✅ 选这个 |
| 混合（n8n 做轻量集成） | 取两者优势 | 维护两套系统 | ⚠️ 可选，但优先自研 |

**结论**：核心业务自研，用 Codex 加速开发。轻量的通知转发等可以后期接 n8n。

### 14.3 部署架构（初期）

```
┌─────────────────────────────────────────────────────┐
│                    单台服务器（初期）                  │
│  ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌─────────┐ │
│  │ FastAPI  │ │ Celery   │ │ Celery   │ │ Vue     │ │
│  │ API      │ │ Worker   │ │ Beat     │ │ (静态)   │ │
│  └──────────┘ └──────────┘ └──────────┘ └─────────┘ │
│  ┌──────────┐ ┌──────────┐ ┌──────────┐             │
│  │PostgreSQL│ │  Redis   │ │  MinIO   │             │
│  └──────────┘ └──────────┘ └──────────┘             │
└─────────────────────────────────────────────────────┘
                        │
          ┌─────────────┼─────────────┐
          ▼             ▼             ▼
    平台 API        LLM API      企微/飞书
```

**扩展路径**：单机试点 → API/Worker 分离 → 数据库与备份独立 → 只读副本 + 分区。只有在容量和运维收益明确时才引入 K8s，避免为了架构而架构。

### 14.4 SLI、SLO 与错误预算

| 能力 | SLI | Phase 1 目标 | 降级策略 |
|---|---|---|---|
| 管理后台 API | 成功请求可用率、p95 延迟 | 月可用率 ≥99.5%；p95 <500ms（不含外部平台耗时） | 只读模式 |
| 订单数据 | 平台更新时间到入库时间 | 95% <30 分钟；99% <2 小时 | 展示数据新鲜度并告警 |
| 定时任务 | 首次成功率 / 重试后最终成功率 | 分别 ≥98% / ≥99.5% | DLQ + 人工重跑 |
| 报表 | 在承诺窗口内生成比例 | ≥99.5%，允许 30 分钟延迟窗口 | 输出带“数据不完整”标识的降级报表 |
| 平台写操作 | 正确执行且无重复比例 | 100% 幂等；任何严重误写即停机复盘 | 自动触发平台/店铺 Kill Switch |

错误预算耗尽时暂停新功能和自动化放权，优先修复稳定性。

### 14.5 备份、灾备与恢复

- PostgreSQL：每日加密全量备份 + 持续归档/PITR；备份与生产机分离存储。
- 对象存储：开启版本控制、生命周期和服务端加密；报表与素材按分类保留。
- Redis 不作为唯一事实来源；队列任务、审批和游标必须在 PostgreSQL 持久化。
- Phase 1 目标：核心交易数据 RPO ≤15 分钟，RTO ≤4 小时；最终以业务影响评估签字为准。
- 每季度至少完成一次恢复演练，并记录实际 RPO/RTO、缺失数据和整改项。
- 备份中的 PII 仍受保留和删除政策约束；恢复后需重新执行到期数据清理。

### 14.6 事件响应与运行手册

- 按 P0/P1/P2 建立值班、升级、通知、止损、取证、恢复和复盘流程。
- P0 安全事件应具备 24 小时通知计划；Amazon SP-API 应遵循其数据保护政策与安全评估要求。
- 每个适配器必须有 Runbook：授权失效、429、平台 5xx、数据延迟、部分成功、字段变更、补数和回滚。
- 监控与告警系统不得与全部生产组件放在同一故障域；单机试点至少把备份和外部可用性探测放在独立位置。

## 15. 数据模型（核心表设计）

### 15.1 设计原则

- **平台差异用 JSONB 兜底**：统一字段用标准列，平台特有字段进 `platform_raw` JSONB，避免为每个平台加字段
- **时间口径明确**：所有表区分 `created_at`（业务发生）和 `synced_at`（入库时间）
- **软删除 + 版本**：商品、价格等关键数据保留历史版本
- **租户与店铺隔离**：所有业务表必须有 `tenant_id`；店铺数据同时包含 `shop_id`，唯一键必须包含租户边界
- **原始层与规范层分离**：原始报文不可变归档，规范化表保存解析版本和来源哈希

### 15.2 数据目录、分类分级与血缘

| 等级 | 示例 | 默认控制 |
|---|---|---|
| L0 公开 | 公开商品标题、公开价格 | 可用于分析，但仍需确认数据来源许可 |
| L1 内部 | 任务状态、非敏感配置、聚合指标 | 登录可见，按最小权限访问 |
| L2 敏感商业 | 成本、利润、广告策略、供应商信息 | 店铺/角色隔离，导出审计 |
| L3 PII | 姓名、地址、电话、邮箱、买家标识、消息正文 | 字段级加密/令牌化、短保留、严格授权 |
| L4 凭据 | Token、refresh token、密钥 | 专用密钥服务或信封加密，应用不展示明文 |

每个数据字段必须登记：业务目的、来源、Owner、分类级别、存储区域、保留期、下游、脱敏方式、删除规则和法定/合同依据。报表指标必须能追溯到源表、转换版本和关账版本。

### 15.3 PII 最小化与生命周期

- 默认不采集业务不需要的买家字段；能用订单 ID 或不可逆哈希完成关联时，不保存明文身份信息。
- PII 不得进入普通日志、告警群、测试数据、分析埋点或未经批准的 LLM 请求。
- Amazon 受限数据按 Restricted Data Token 和适用角色访问；遵循 Amazon 数据保护政策、强制安全评估、加密和访问控制要求。
- Amazon 官方安全概述明确要求对 PII 执行 30 天删除规则并验证备份加密；具体字段与例外由安全负责人对照最新政策确认。
- 支持访问、更正、删除请求的工单与执行记录；删除需传播到缓存、搜索索引、对象存储和可控备份生命周期。
- 生产数据禁止直接复制到开发/测试环境；测试使用合成或脱敏数据。

### 15.4 跨境数据与供应商治理

- 在数据进入 LLM、对象存储、通知渠道或海外服务器前，记录数据类别、来源地区、目标地区、处理目的和供应商。
- 由法务确认 PIPL/DSL/CSL、GDPR/UK GDPR、CCPA/CPRA、平台数据政策及合同要求的适用性。
- 维护供应商和子处理者清单：数据保留、是否用于训练、加密、事件通知、删除能力、数据中心区域和退出方案。
- 默认采用“先脱敏、后外发”；不能证明合规的数据不得发送到外部模型。
- 更换模型供应商、云区域或通知渠道视为数据流变更，必须重新评审。

### 15.5 审计与日志脱敏

- `audit_events` 记录业务操作事实；`api_call_logs` 只记录排障元数据，两者职责分离。
- 请求/响应只允许白名单字段，Token、Cookie、Authorization、地址、电话、邮箱和消息正文默认移除或令牌化。
- 敏感报文采样需工单审批、短有效期、专用权限和自动销毁。
- 审计日志记录前后值哈希、操作者、审批链、时间、设备/IP、幂等键和结果；采用 append-only 存储并定期校验完整性。

## 16. AI 治理与模型运营

### 16.1 用例风险分级

AI 能力按风险分级管理，高风险场景不允许无人工干预自动执行：

| 风险级 | 用例 | 允许的输出形态 | 上线要求 |
|---|---|---|---|
| 低 | 摘要、翻译、结构化抽取、内部检索 | 可直接供人参考 | 抽样评估 + 成本监控 |
| 中 | 消息意图分类、情绪识别、标题/描述建议、素材文案建议 | 建议 + 置信度，人工确认 | 黄金集达标 + 灰度 |
| 高 | 客户对外回复、退款判断、改价建议、侵权/合规判断、利润归因结论 | 仅建议，必须人工审批 | 双人复核 + 严重错误零容忍 + 可追溯 |
| 禁止自动 | 无审批的退款、改价、下架、对外承诺 | — | 系统层面阻断 |

### 16.2 版本与可追溯

每次 AI 调用必须记录：

```text
model_id / model_version / provider
prompt_template_id / prompt_version
eval_dataset_version / rule_version
input_hash（不记录原文，或按 PII 政策记录脱敏摘要）
output_schema_version
latency / token 用量 / 估算成本 / 是否降级 / 是否人工改写
```

模型、提示词、规则和评测集任一变更都必须版本化，可通过版本号复现历史判断。禁止在生产环境直接编辑线上提示词。

### 16.3 离线评测与上线门禁

- 建立冻结黄金集，按语言、品类、意图和风险等级分层。
- 分类任务指标：宏平均 F1、高风险召回率、置信度校准（ECE）。
- 生成任务指标：事实一致性、平台规范符合率、禁用词命中率、人工改写率。
- 高风险场景要求严重错误率 = 0，不达标不得扩大自动化范围。
- 评测集禁止混入生产 PII；使用合成或脱敏数据，并保留构造记录。
- 上线流程：离线评测 → shadow（不对外）→ canary（小流量）→ 灰度 → 全量，每阶段定义回滚条件。

### 16.4 提示词注入与内容安全

- 买家消息、商品页、竞品页面、导入文件全部视为**不可信输入**。
- 系统提示与用户内容严格分离，禁止将外部文本直接拼接进高权限指令位置。
- 工具调用与生成内容隔离；模型输出不得直接作为 Shell、SQL 或平台 API 参数执行，必须经过结构校验与白名单。
- 输出经规则层校验：禁用词、金额上限、承诺词、链接、PII 回显。
- 检测到疑似注入时记录安全事件并降级为人工处理。

### 16.5 漂移监测与回滚

- 持续监测准确率、拒答率、人工改写率、成本/请求和延迟；指标突破阈值自动告警。
- 模型或平台版本变更视为风险变更，需重新评测。
- 支持一键将提示词/模型版本回滚到上一个已验证版本。
- 人工纠正结果回流为评测与优化数据，但必须经审核后入库，不得自动训练。

## 17. Codex 协作方案（重要）

### 17.1 Codex 在项目中的角色定位

**Codex 是开发引擎，不是运行时组件。**

| 场景 | Codex 做什么 | 不适合做什么 |
|---|---|---|
| 开发期 | 写代码、写测试、重构、修 bug、写文档 | — |
| 代码审查 | 自动 review PR、检查规范 | — |
| 维护期 | 修复线上 bug、加新平台适配器 | — |
| **运行时** | ❌ 不参与 | 运行时用 LLM API（业务逻辑内的 AI 能力） |

**因为**：Codex CLI 是开发工具，运行时调用它做客服分类、素材生成既不经济也不稳定。运行时用 LLM API 网关。

### 17.2 AGENTS.md 项目规则设计

Codex 每个会话启动时构建一次指令链（root → cwd，越靠近 cwd 优先级越高，总上限 32KiB）。为此设计分层规则：

```
项目根 AGENTS.md                      # 全局：架构约定、技术栈、通用规范
  ├── apps/api/AGENTS.md              # 后端：FastAPI 约定、DB 规范、测试要求
  ├── apps/worker/AGENTS.md           # 任务：Celery 约定、幂等性要求
  ├── apps/web/AGENTS.md              # 前端：Vue 约定、组件规范
  ├── adapters/amazon/AGENTS.md       # 平台适配器专属：SP-API 的坑
  ├── adapters/temu/AGENTS.md         # Temu 专属：区域隔离、签名
  └── adapters/tiktok/AGENTS.md       # TikTok 专属
```

**根 AGENTS.md 骨架**（控制在 1-3 KiB）：

```markdown
# EC-AutoFlow 项目规则

## 架构约定
- 分层：API 层薄（解析→调 Service→返回），业务逻辑在 services/，数据访问在 repositories/
- 平台差异一律通过 adapters/ 抽象，业务代码禁止出现 if platform == "amazon"
- 所有外部 API 调用必须走 adapters 的统一接口 + 限流器
- 所有金额用 Decimal，禁止 float；所有时间用 UTC 存储，展示层转换

## 数据规范
- 平台特有字段进 platform_raw JSONB，不新增列
- 关键表必须有 created_at / updated_at
- 变更类数据（价格、库存、排名）只追加，不覆盖

## 测试纪律
- 声明完成前必须跑：`uv run pytest -q`
- 新增 adapter 必须有 mock 测试覆盖：认证、限流、错误分支
- 涉及金额计算的代码必须有单元测试，覆盖边界（退款、部分退款、汇率）

## Things not to do
- 禁止在业务代码里硬编码 API 密钥（用 environ / secrets manager）
- 禁止裸调 requests 打平台 API（必须走 adapter + 限流）
- 禁止在未加幂等保护的情况下写同步任务
- 禁止删除 migrations 历史文件

## 工具使用
- 查数据库结构优先用 postgres MCP，不要猜字段名
- 查平台 API 文档优先用 fetch，不要凭记忆写接口
```

**适配器专属 AGENTS.md 示例**（adapters/amazon/AGENTS.md）：

```markdown
# Amazon SP-API Adapter 规则

## 必读坑位
- 区域 Base URL 三套：NA/EU/FE，必须按 shop.region 路由，否则 404
- Listings Items API 限流严格，批量一律走 Feeds API
- Feeds 提交是异步的，必须轮询 processingReport，提交成功 ≠ 上架成功
- 属性字段必须从 Product Type Definitions API 动态获取，禁止硬编码
- 上架前必须先查 Listings Restrictions 确认类目是否受限

## Ads API 特别注意
- 两套 Header 不能混用：v1 用 Amazon-Ads-*，SP v3 用 Amazon-Advertising-API-*
- Media-Type 极易写错：Create 用 spAdGroup（大写 A），List 用 spadGroup（小写 a）
- 自动投放的 Target 只能 List + PUT Update，不能 Create
- 返回 207 不代表全成功，必须解析 body 里的 error 字段

## 完成前检查
- [ ] 所有接口调用有指数退避 + 抖动
- [ ] refresh_token 加密存储
- [ ] 有 mock 测试覆盖 429 / 401 / 500
```

### 17.3 用 Codex 开发的实际工作流

```
1. 需求 → 在 PRD 里找到对应模块章节
2. 建任务 → 用 Codex 生成骨架：「按 AGENTS.md 规范，实现 Amazon 适配器的
   create_listing，参考 adapters/base.py 的接口定义」
3. 生成 TDD → 先让 Codex 写测试，再写实现
4. 本地验证 → 跑 pytest，跑沙箱联调
5. 自动审查 → 开启 auto_review，每次提交前自动 review
6. 人工 review → 关注业务逻辑正确性，不关注格式
7. 合并部署
```

### 17.4 提效技巧

| 技巧 | 说明 |
|---|---|
| **并行 subagent** | 大任务拆成 3 个子任务并行跑（如同时实现 3 个平台适配器） |
| **MCP 接入** | 接 postgres MCP 让 Codex 直接查表结构；接 fetch 让它查 API 文档 |
| **hooks 自动化** | `post-edit` 钩子自动跑相关测试，`pre-commit` 自动 lint |
| **CI 免登录** | CI 里设 `OPENAI_API_KEY` 跳过 OAuth |
| **推理强度** | 复杂任务用高推理，日常改动用默认，避免成本和延迟失控 |
| **定期验证规则** | 季度检查哪些 AGENTS.md 实际没被加载（32KiB 上限容易静默截断） |

### 17.5 安全约束

- **敏感操作必须人工确认**：改价、批量下架、退款执行、删除数据
- **Codex 不得自动 push 到主分支**：所有变更走 PR + review
- **密钥不进代码**：一律环境变量 / 密钥管理服务
- **AGENTS.md 视为"项目规则"而非"可信指令"**：多人协作时，改动 AGENTS.md 需 code review

| 模块② 上架 | 模板与草稿生成 + 校验 + 人工审批 + 小批量上架 + 结果回查 |
| 模块③ 素材（基础） | 白底图 + 卖点图 + 合规检查（不含 AI 场景图） |
| 模块⑤ 财务 | 结算报告拉取 + 履约贡献利润 + 对账（两个已关闭周期） |
| 模块⑦ 报表 | 经营日报 + 库存预警 + 结算对账报表 |
| 灰度机制 | 20 SKU → 100 SKU 分批放量 + 回滚演练 |

**里程碑**：1-2 个真实店铺连续 14-30 天只读 Shadow 运行，随后完成 20 SKU 审批制上架，并产出经财务确认的对账结果。

**Phase 2：数据智能（6-8 周）**

| 交付 | 说明 |
|---|---|
| 模块① 选品 | 经授权数据源 + 评分卡 + 选品巡检 + 选品表（含置信度） |
| 模块③ 素材升级 | 场景图、详情长图（需评测与成本上限） |
| 模块⑤ 财务升级 | 广告归因 + 成本模型反哺（财务签字后） |
| 模块⑦ 报表升级 | 广告日报、周月报、利润下钻 |
| 模块⑥ 扩展 | 第 2 个平台适配器（按能力矩阵落地） |
| AI 治理 | 黄金集、评测流水线、版本管理与灰度能力 |

**里程碑**：选品巡检产出带评分、来源和置信度的候选清单；AI 评测流水线可回归。

**Phase 3：监控与自动化（6-8 周）**

| 交付 | 说明 |
|---|---|
| 模块⑧ 竞品监控 | 经授权来源 + 价格/活动/排名/评论监控 + 三级预警 + 建议动作 |
| 模块④ 客服售后 | 消息接入（按平台能力）+ 分类 + **建议回复** + 退货规则化处理 |
| 模块⑦ 报表完善 | 竞品监控日报、售后统计报表 |
| 运维后台 | 任务管理、阈值配置、日志查询、指标字典、权限复核 |
| 自动化放权 | 白名单低风险场景可自动执行，高风险保持审批 |

**里程碑**：经授权竞品价格变动在 SLA 内捕获并给出建议；分类黄金集达标；低风险退货单规则化处理。

**Phase 4：规模化（持续）**

- 按能力矩阵增加平台，优先选择“能力高、合规清晰、成本可控”者。
- 容量、成本与 SLO 优化；错误预算稳定后才提升自动化等级。
- 选品评分模型用真实数据持续校准。
- 评估是否引入 Temporal、数据仓库与 BI。

### 18.2 优先级原则

如果资源有限，按这个顺序做：

```
1. 平台对接（没这个啥都做不了）
2. 报表 + 财务（老板最关心，最快看到价值）
3. 上架自动化（人力节省最直观）
4. 选品（价值最大但最难，依赖前面数据积累）
5. 竞品监控（独立性强，可并行）
6. 客服售后（依赖平台 API 权限，可能受阻）
7. 素材（可先用人工 + AI 辅助过渡）
```

## 19. 风险与对策

| 风险 | 影响 | 概率 | 对策 |
|---|---|---|---|
| **平台 API 权限申请受阻** | 模块⑥⑦⑧无法落地 | 高 | 提前 1-2 个月申请；准备降级方案（导出文件导入） |
| **TikTok 客服 API 审批不过** | 模块④受阻 | 高 | 降级为 CSV 导入 + 人工回复辅助 |
| **Temu 预备金与门槛** | 无法对接 Temu | 中 | 评估成本收益；或先用第三方 ERP 中转 |
| **平台限流/风控封禁** | 数据中断 | 中 | 严格限流、指数退避、降频和熔断；达到限制即停采或切换授权数据源；**禁止使用多账号或代理规避平台限制**；遵守平台条款与数据政策 |
| **PII 泄露或违规跨境传输** | 监管处罚、账号被封 | 中 | 数据分类分级、最小化采集、默认不外部传输、供应商审查、密钥加密、日志脱敏、24 小时事件通知 |
| **AI 幻觉导致错误承诺或误操作** | 客户纠纷、经济损失 | 中 | 用例风险分级、黄金集评测、人工审批、白名单自动范围、输出校验、灰度与回滚 |
| **审计缺失导致无法追责** | 无法定位损失、内控失效 | 中 | append-only 审计、审批链留痕、职责分离、季度权限复核 |
| **数据准确性不足** | 决策错误 | 中 | 多源交叉验证；标注置信度；人工终审 |
| **AI 分类/生成质量不稳定** | 影响体验 | 中 | 建标注集评估；人工可纠正；关键场景不自动执行 |
| **自动执行出错（误改价/误退款）** | 直接经济损失 | 低但严重 | 资金相关操作强制审批；设置金额上限；操作留痕可回滚 |
| **合规风险（侵权/认证）** | 商品下架、账号风险 | 中 | 上架前强制合规检查；侵权词库；认证要求提示 |
| **数据安全（Token 泄露）** | 店铺被操控 | 低但严重 | Token 加密存储；最小权限授权；操作审计 |
| **范围蔓延** | 项目失控 | 高 | 严格按第 2.3/2.4 节非目标与 MVP 边界裁剪；每期只做计划内的事，新增需求走变更评审 |
| **单人/小团队维护压力** | 长期不可持续 | 高 | Codex 提效仅覆盖编码环节；必须落实第 18.0 节 RACI 与运维值班，或明确接受降级为“单店铺辅助工具” |
| **预算失控（AI/采集/存储）** | 成本高于收益 | 中 | 单位成本跟踪、月度熔断、缓存去重、分级使用模型 |
| **依赖单一外部平台政策变化** | 核心能力失效 | 中 | 能力矩阵 + 降级路径 + 官方文件导入兜底；不把单一平台 API 当作唯一事实来源 |

### 19.1 最需要提前启动的事

**平台 API 权限、数据来源授权与合规结论周期最长，必须第一天就开始**：

1. Amazon SP-API 开发者注册 + 应用创建（需开发者账号，可能要审核）
2. Amazon Ads API 申请（scope 申请）；如需 PII 能力，另行申请受限数据角色并落实安全要求
3. TikTok Shop 开发者账号与卖家授权；客服能力单独确认审批要求
4. 其他目标平台开放平台账号，逐平台核验授权与商务门槛（含 Temu，须以官方书面规则为准）
5. 选品/竞品数据源的授权与法务结论（含 Google Trends Alpha 申请状态）
6. 数据分类分级、PII 流向、部署区域与 LLM 供应商的合规评审

### 20.4 Go/No-Go 门禁

**立项 Go（全部满足）**

- [ ] MVP 平台、区域、店铺、履约模式、数据容量与排除项已签字。
- [ ] API 权限或可验证的降级路径已取得。
- [ ] 数据分类、PII 流向、部署区域和 LLM 供应商已获安全/法务批准。
- [ ] 财务 Owner 已签署指标字典、成本计价、分摊与关账政策。
- [ ] 预算上限、RACI、上线 Owner 与运维 Owner 已确定。
- [ ] 所有自动写操作具备审批、审计、幂等、限额和 Kill Switch。

**生产 Go（全部满足）**

- [ ] 完成 14-30 天只读 Shadow 运行，数据质量与时效达标。
- [ ] 契约测试、数据回放、财务对账和 UAT 通过。
- [ ] PII 未出现在普通日志、告警、测试数据和未经批准的 LLM 请求中。
- [ ] 备份恢复演练达到 RPO ≤15 分钟 / RTO ≤4 小时。
- [ ] AI 黄金集按语言与风险场景通过，严重用例无漏转人工。
- [ ] 先 20 SKU 灰度、再扩至 100 SKU，未突破错误率与资金风险阈值。
- [ ] 回滚、暂停同步和撤销写操作流程已演练。

**任一命中即 No-Go**

- 未取得合法 API 或数据来源授权；
- 无法确认买家 PII 或客服消息的跨境流向；
- 高风险写操作可绕过审批；
- 日志仍完整保存 Token、买家信息或消息正文；
- 财务口径未由财务负责人确认；
- 恢复演练失败或无可用备份；
- 单位成本超过预算且无熔断；
- 严重 AI 错误可直接触发退款、改价或对外承诺；
- 没有可执行的停机和回滚方案。

### 20.5 生产就绪评审与运营交接

- 每个适配器具备 Runbook、Owner、值班联系人和升级路径。
- 权限矩阵完成首次复核，临时授权设定到期时间。
- 指标字典与关账政策发布，相关人员完成培训。
- 告警分级、静默规则、值班表和复盘机制生效。
- 变更管理：高风险变更需评审、灰度与回滚方案。
